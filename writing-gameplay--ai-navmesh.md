# Writing gameplay: AI navmesh navigation — skill pack

> Lane sub-file for `writing-gameplay`. Load `_core.md` and `writing-gameplay.md` first.
> Navmesh generation, bounds, pathfinding, and world-representation staleness for AI agents.
> Sanitized public advice; the sync appends new bullets here.

- **The navmesh voxeliser erodes every walkable surface away from obstacles by the agent radius ROUNDED UP TO A WHOLE CELL, from both sides, so an opening of clear width W leaves `W - 2 * ceil(agentRadius / cellSize) * cellSize`, and if that is under one cell there is no navmesh through the opening at all.** Symptom shape: a generated building reachable on 3 of 6 units at one seed, the failing set changing with the seed; it reads as a generator bug and it is arithmetic. Derive the clearance minimum from the AGENT, do not author it: write the floor as `2 * agentRadius + 2 cells` and lint the art library so it cannot go under it. One surviving cell is a failure, not a pass, because it survives by where it falls on the lattice; budget two spare cells and prove it by moving the lattice. `NavMesh.CellSize`/`CellHeight` exist but are not on the game assembly access list, so sweep the opening width and find where the connection appears instead. Build a CHAIN probe that asks for a path between each adjacent waypoint before the third hypothesis: it turns "did it get upstairs" into an address.

- **`NavMesh.Bounds` is a READBACK; `NavMesh.CustomBounds` is the switch that makes an assignment mean anything.** Assigning `Bounds` while `CustomBounds` is false is discarded on the next generation, and the property reads back fine in between, so the code that sets it looks correct and logs a success while every generation keeps using the authored box. Any experiment that moves the navmesh bounds has to set `CustomBounds = true` FIRST, or it is measuring the box it thinks it changed.

- **A `Partial` path's `Points` are NOT truncated where the search actually stopped, so the last point of a failed path is somewhere the agent cannot reach; judge reachability on `Status` ALONE.** Reading the final point as where it got to produced a whole results table reading "reaches the landing, engine labels it Partial" for units whose agents never left the ground floor.

- **A baked navmesh is a separate, cached, DERIVED copy of the world: a door leaf that has swung clear in the physics world leaves the navmesh exactly as it was baked, so the doorway stays solid to every agent while a player walks through it.** Both halves of a project pass their own tests over that: a player is a capsule on the PHYSICS world so a door battery grades all doors correct, and an NPC is an agent on the NAVMESH so a defender that never leaves its room looks like it is holding post. Fix: request a TILE regeneration around the doorway when a leaf finishes moving, the same call a destructible wall makes. Two rules past doors: when a system edits the world, list every REPRESENTATION it must edit (physics, navmesh, occlusion, audio propagation, cached cover points, a lighting bake), each a derived copy that goes stale on its own terms; and a capability flag (`CanMove = Scene.NavMesh.IsEnabled`) is not evidence of the behaviour, so when a pass adds a mover, assert that it MOVED somewhere it could not have started.
