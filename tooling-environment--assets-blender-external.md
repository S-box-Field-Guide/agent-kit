- **Reusing another project's assets = copy with identical root-relative paths.** vmdl
 files reference their .obj and .vmat by project-root-relative path, so copying
 `models/tree_oak.*` + `materials/flat/*.vmat` +
 `materials/textures/white.png` into the same subfolders of the new project
 works with zero edits. Copy the source files only (.obj/.mtl/.vmdl/.vmat/.png), not
 the compiled `*_c`.

- **Kenney's own nature pack is an even
 easier zero-edit borrow than another project's**: every vmdl there references its mesh as
 `models/kenney/nature/<name>.fbx` and a SHARED `models/kenney/nature/materials/*.vmat`
 folder (one universal `DefaultMaterialGroup` remap table, identical across all 20
 vmdls), and every one of those vmats points only at the ENGINE's own
 `materials/default/default_{color,normal,rough}.tga` — no project-local textures at
 all, just a `g_vColorTint` per material. So copying the vmdl+fbx pair for each chosen
 species plus the whole `materials/` folder into the same `models/kenney/nature/`
 subpath in the new project needs LITERALLY zero path edits. Kenney's `nature/` folder is the source for trees/pines/bushes/rocks/flowers/cliffs. Kenney's pack has NO
 dedicated grass-tuft mesh — reuse a small-scaled `plant_bush.vmdl` as the "tuft" stand-in
 until a real grass model is generated.

- **Model.Load of a MISSING vmdl can return the error model with the REQUESTED path as its Name** - the classic `Name.Contains("error")` check passes and you spawn the engine's giant orange ERROR-text mesh. Robust gate: `model == null || model.IsError || model.Name.Contains("error")`.

- **Blender `materials.clear()` + `materials.new(name)` = the `.001` checkerboard trap.** `mesh.data.materials.clear()` only detaches the datablock from the slot list — it stays alive in `bpy.data.materials`, so a follow-up `materials.new(same_name)` dedup-renames to `name.001`. That `.001` becomes the FBX material slot key, the vmdl remap (listing the clean name) can't match it, and the engine loads `name.001.vmat` → File not found → red checkerboard in-game. The `.001` lives in the FBX *binary* — grepping vmdls finds nothing; grep the `.fbx` bytes. Fix: purge stray `name`/`name.NNN` datablocks and force-rename the slot before export (`sanitize_material_slots` in the quadruped rig library/the NPC rig library). Hit 10 rigs (8 animal rigs plus humanoid rigs); the hero character escaped only because its OBJ used a hyphen where the rig used an underscore.

- **Headless Blender 5.2 drops the old compositor API silently** — `Scene.node_tree` / `CompositorNodeComposite` removed; use `scene.compositing_node_group` + `NodeGroupOutput`, or skip the compositor entirely with an opaque-floor render recipe.

- **Headless Blender opaque-floor render recipe** sidesteps compositor API churn entirely — an emissive-grey world + albedo-matched diffuse floor + the subject's own cast shadow; no film transparency, no compositor graph needed. Use Standard view transform, not AgX.

- **A previously-working Blender --background --python gen.py pipeline can start HANGING INDEFINITELY at full app init (near-zero CPU, no output, Blender --version still instant) — the culprit is Blender USER PREFS/addon state, not the script or the GPU.** Verified on a Windows machine after an s&box editor crash the same day: three consecutive 5-minute hangs with plain --background, then --background --factory-startup -noaudio ran the identical script to completion in seconds (Blender 5.1). --factory-startup skips loading the user preferences and addons, which is where the corrupted state lives; -noaudio removes the audio-device probe as a second known init staller. Fixes: (1) add --factory-startup -noaudio to every headless invocation in pipeline tooling — generator scripts should not depend on user prefs anyway; (2) if prefs are needed, delete/regenerate the Blender user config directory. Diagnostic that separates this from a busted install: --version returns instantly (binary fine) while --background --python stalls (init path).

- **A hand-tune applied to a GENERATED asset's output file (a manifest JSON, an OBJ, a baked config) is silently reverted the next time the generator runs — regen is a clobber, not a merge.** Concrete instance: a live feel-tuning session moved a kit manifest's `driver_seat_author_m` sit point in the generated manifest.json; the Blender generator still carried the old tuple, and a routine 4-kit regen weeks of context later quietly reverted the tuned pose with zero warnings — caught only because the coordinator diffed the regen output against git HEAD before committing. The law: the generator is the SINGLE source of truth — any tune made against a generated file must be back-ported into the generator in the SAME work step, then proven by re-running the generator and byte-diffing its output against the tuned file (identical = parity; any diff = a value still living only downstream). Corollary: always run `git diff` on a regen before committing it — an unexpected changed line in a “should-be-idempotent” regen is exactly this trap firing.

- **A same-pose live-vs-export pixel-diff that hides the live world and spawns the exported block measures the ENVIRONMENT, not the export: the EnvmapProbe's ambient contribution is scene-state-dependent and flaps between captures — disable the skybox+probe GO for BOTH captures or the diff is garbage.** export-v2 §6.2 calibration: a faithful LowPoly export block diffed at interior mean 33/255 vs live with a UNIFORM ~1.30–1.36× per-channel brightness ratio on matched land patches — no UV/material/geometry fault at all. Two live-vs-live captures of the UNCHANGED world minutes apart differed by mean 28.5/255, proving the environment (not the bake) owned the whole diff; on this build the probe swing is ~4× the ~7% the older probe-flip gotcha measured, and the burst-guard (brightest-frame-with-a-twin) does NOT save you because an entire burst can land in one probe state while the other side's burst lands in the other. Fix that makes the gate exact: `set_game_object {id:<2D Skybox go>, enabled:false}` (kills SkyBox2D + EnvmapProbe together) before the LIVE capture, keep it off through the export-block capture, re-enable after. Result on the identical shots: live-vs-live mean 0.0000/255 (max 6), live-vs-export interior mean 0.102/255 p99=1.0 — the M11b ≈0 bar, recovered. Sun + locked Tonemapping exposure ( Min==Max) are stable and stay on; only the probe/sky pair is the noise source. Also check the clock isn't advancing ( paused/anchored) before blaming the bake.

- **A heavy export bake does not end when the MCP call returns: the editor then IMPORTS the fresh asset tree OUT-OF-BAND and goes unresponsive for MINUTES — stacking a second heavy MCP call into that grind is what WEDGES the editor, not the bake itself.** export-v2 calibration: a full-world Smooth bake writes ~2700 loadable assets (obj/mtl/vmdl/vmat/png/ prefab per land+water chunk); after returns its result JSON the editor asset-imports that tree and the MCP server answers slowly or not at all for ~15-20 min, then RECOVERS on its own. It survives ONE bake's import queue, but under 4 stacked bakes + a regenerate with no gap it wedged PERMANENTLY (needed the kill/relaunch recovery — see g-tool-hung-editor-kill-relaunch). Fix baked into the export runner (tools/.py): (a) give the MCP call a long ceiling (1800s) so the blocking bake write never times the client out; (b) after EVERY export — including the reexport-identical SECOND bake — DRAIN- WAIT: poll editor_status on a short (15s) timeout and only proceed once it answers promptly ~3 CONSECUTIVE times, so the next heavy step never lands on a digesting editor. Space all heavy ops; never poll-spam mid-bake (an ACTIVE, growing logs/sbox-dev.log means it IS working — wait, don't restart). Only treat it as hung if MCP is dead >25 min AND the log has stopped growing. ROOT CAUSE (nailed after a terminal wedge — 80+ min unresponsive, 10.2 GB working set, killed): every same-slot re-export DELETES + REWRITES the whole bake folder, which invalidates every compiled asset in it — the asset system then queues an on-demand recompile of the entire tree ("At least one out-of-date dependency: … (file stopped existing)" per asset in sbox-dev.log), so each re-export wave costs a full-tree recompile and STACKED waves in one warm session are UNBOUNDED churn; drain-wait spaces the waves but cannot shrink them. The durable fix is STRUCTURAL: standing regression suites bake SMALL worlds ( ruling 2026-07-14 — 192 cells / 36 chunks; bake + same-slot re-export + drains ≈ 25-40 s end-to-end, drains answer in 10-17 s) and full-scale bakes are ONE-TIME proofs recorded in the spec descriptions, never re-run as a standing gate.

- **A gitignored `Assets/exports/` bake tree whose SOURCE `.obj` were deleted but whose compiled `.vmdl` remain is a PERMANENT on-demand recompile loop that a FRESH editor re-enters and never drains — and its real damage is that it STARVES play-mode init, so it reads as "really low FPS in play" when the editor is actually just grinding.** Distinct from the in-session export churn (`g-tool-…export…recompile`, which drains in ~15-20 min): here the source is *permanently* gone (prior same-slot export-v2 re-export deleted the `.obj`), so the asset system logs `On-demand recompile of asset exports/…vmdl -> reason: … dependency: …obj (file stopped existing)` forever over a bounded ~20-asset working set (sampled: the last asset repeated every 6 s across 30 s; 1624 stale vmdls, 6.4 GB working set, console 100 % saturated so NO game/`[wb]` line is observable even in a 2000-line buffer). SYMPTOM MASQUERADE (the trap): with the storm live, `play_start` returns but `` shows `gameLive=false`/`frames=0` and the census falls back to the edit scene — the play world never builds — across 45 s. Looks like a play-mode perf/day-night problem; it is a stalled editor. RECOVERY (the live editor holds file handles, so `mv`/`rm` of `Assets/exports` fails `Permission denied`, and the auto-mode classifier blocks `rm -rf` of an unnamed repo dir): (1) `Stop-Process -Force` ONLY the editor PID (verify by window title `<scene> - s&box editor`; never a sibling project's), (2) `Move-Item` the gitignored `Assets/exports/` OUT of the tree (regenerable via ``; handles freed once the process is dead), (3) relaunch via the captured CLI — mind the `McpServerPort` bind-fail follow-on (`g-tool-mcp-bind-fail-no-auto-bump-edit-pref-restart`: the global pref may hold a sibling's port). After: play inits normally and holds a locked 60.

- **To close a byte-identical dent-hash ×N gate that a DRIVEN run-up flakes (`g-tool-driven-approach-dent-hash-nondeterministic`), inject a SYNTHETIC impact with a FIXED BODY-LOCAL contact through the real damage path — the resulting dent is pose-invariant, so the hash is byte-identical regardless of where/settle the car is.** D2 `crashpin`: a harness hook builds the world contact as `bodyTx.PointToWorld(fixedContactBodyLocal)` and calls the same `ProcessImpact` a real collision uses (attribution + dent kernel + coupling). Because the dent is stored in PART-local space and the part rides the body rigidly, `partTx.PointToLocal(pointWorld)` depends only on the fixed body-local contact and the fixed body↔part relative transform — NOT on the car's world pose. Result: combined dent-hash byte-identical ×3 across fresh `play_start`s (vs the driven approach which drifted ~0.15 mm and flipped 1 of 3). It exercises the real damage CODE (only the physics collision detection — the actual nondeterminism source — is bypassed), so it is a legitimate determinism gate, not a stub. Pin the car pose too as belt-and-suspenders, but the pose-invariance is what actually guarantees the byte-identity.

- **Regenerating a Blender-exported asset kit on a NEWER Blender than the one that built the committed assets rewrites EVERY exported `.obj`/`.mtl` with cosmetic-only deltas — an exporter version-header line and an unused `Ns` value in the `.mtl` — so a naive "commit the regen" sweeps ALL N parts (30 in sedan_kit) into a diff where only the target parts actually changed geometry.** Clean pattern: (1) run a baseline regen with the UNMODIFIED generator first and confirm the diff is cosmetic-only; (2) make the real change and regen; (3) selectively revert every non-target part before committing, so the commit carries only real geometry changes. JSON manifests are immune (no version string in them). Related gotcha: with `core.autocrlf=true`, editor-reserialized `.vmdl` files show `status=M` with an EMPTY git diff (line-ending-only) — verify with a content diff before assuming a `.vmdl` actually changed. ( sedan_kit regen, Blender 5.2 vs committed 5.1.2 assets, commit d78f772, 2026-07-16)

- **A PARTIAL rebuild (regenerating only some assets in a batch) must regenerate the manifest's aggregate/summary HEADER from scratch — never merge the new per-asset entries into the OLD header carried forward from a prior full run — or the header's summary fields (dimensions, counts, bounds) silently drift stale relative to what's actually in the batch.** A manifest built by a generator that only touches the assets it was asked to touch, but writes its header by patching the previous JSON in place, ends up with a header describing a batch that no longer matches the file's own body (STALE-DIMENSION DRIFT) — the discrepancy is invisible until something downstream trusts the header instead of recomputing from the entries. Related but distinct from `g-tool-regen-clobbers-hand-tuned-values-in-generated-assets` (that entry is about a FULL regen clobbering a hand-tune; this one is about a PARTIAL regen failing to refresh its own summary data). Fix: always recompute the manifest header from the full current entry set on any rebuild, partial or not — treat "merge the header forward" as a bug pattern, not an optimization.

- **A render-rig capture script that positions the camera with ABSOLUTE world coordinates is a radius-drift landmine — any change to the subject's size, position, or the orbit radius silently reframes or misses the shot, and nothing catches it until someone looks at the output.** Absolute coordinates bake in an assumption about where the subject sits that the next asset (a different size, a moved spawn point, a re-tuned orbit distance) breaks without any error — the script still runs, it just points the camera at the wrong place. Fix: build camera placement from FRAME-RELATIVE helpers (subject bounds/center + a relative offset or orbit radius derived from the subject, not a hardcoded world position) so the same script keeps framing correctly as the subject changes.

- **A Blender BEVEL modifier does not interpolate UVs reproducibly — rebuilding the identical source mesh twice can land a beveled corner's UV on either of exactly two answers one float32 apart, decided per process, while geometry and topology stay byte-stable.** Over twelve rebuilds of one model, vertex coordinates and loop topology were byte-identical every run while ~2% of UV components flipped between two states, largest move one ULP (`5.96e-08`); the wobble reaches the exported file because a few UVs sit within `1e-8` of a rounding boundary the fixed-decimal exporter resolves either way. Don't file it as a real asset change — it is exporter nondeterminism at the last bit; confirm with a repeat build before treating a UV-only diff as meaningful.
