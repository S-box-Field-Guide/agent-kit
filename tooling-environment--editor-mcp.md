# Tooling & environment — editor & MCP

> Topic sub-file of this lane — router: `tooling-environment.md` (its "Where everything lives"
> table maps every topic). Load `_core.md` first. Bullets below are moved verbatim
> from the lane pack; the sync appends new bullets for these topics here.

- **A one-shot "commandeer + suspend competing drivers" sweep misses components created
 AFTER it runs** — one project's benchmark flythrough suspended everything on the camera
 GameObject at scene start, but Bootstrap.StartPlay creates ChaseCamera on that same
 GameObject ~1 s later (menu -> play transition), so it was never suspended and fought the
 flythrough every frame (its leash invariant hard-snapped the camera back to the player
 every ~2 s -> the visible "camera disjointed / sliding away"). Any commandeer pattern must
 either re-sweep for newborn drivers every tick (cheap on one GameObject) or hook the
 creation path; a suspension list built once is a scope-hole of the same class as a
 one-shot audit exemption. Diagnosis shortcut: if a misbehavior's telemetry warns cluster
 EXACTLY inside another system's active window, suspect a two-writers fight, not a broken
 writer.

- **The editor compiler can crash internally (NullReferenceException, "One or more errors
 occurred") and WEDGE: `compile_status` then reads `success=False` with 0 errors/0 warnings
 AND `needsBuild=False`** — it thinks nothing needs rebuilding while the last compile failed,
 so the editor silently keeps running the stale assembly forever. No code error exists to fix.
 Recovery: bump any watched source file's mtime (PowerShell `(Get-Item file.cs).LastWriteTime
 = Get-Date`) to dirty the compile; it rebuilds clean. Detect via the MCP `compile_status`
 (success=False + 0 diagnostics + needsBuild=False is the wedge signature).

- **The s&box editor runs an MCP server on `http://127.0.0.1:7269/mcp`** — the
 headless verification loop for assets. Launch `sbox-dev.exe -project <sbproj>` in
 the background, then JSON-RPC `tools/call` → `call_tool` wrapping: `asset_compile`
 (returns Success/CompiledFile — THE way to verify a vmdl compiles), `asset_info`,
 `spawn_model` + `set_editor_camera` + `editor_camera_screenshot` (base64 PNG — eyes
 in the engine: verify orientation/scale against a known-good model side by side),
 `read_console`, `play_start/stop`, scene CRUD. `list_toolsets`/`describe_toolset`
 to discover schemas. Spawned objects live in the unsaved scene — don't save and
 they clean themselves up on exit.

- **Never publish live mutable static Lists to per-frame consumers — hotload's ListUpgrader reallocates them mid-tick.** NavData exposed `static readonly List<Vector3> StreetLoop` that the builder `Clear`+`Add`ed and every GuardNpc/Wanderer indexed each frame. A hotload (or rebuild) reallocates/shrinks the backing array BETWEEN a consumer's `Count` read and its `list[i]` — IndexOutOfRange every frame on every consumer at once, even ones with modulo guards (the race is on the list, not the index). The log smoking gun: `[hotload/GameMenu] Destination array is too small … ListUpgrader`. Fix: publish `IReadOnlyList<T>` and REBIND the field to a fresh list per rebuild (one atomic reference assignment); consumers capture `var loop = NavData.StreetLoop` once per tick and get an immutable snapshot. Belt-and-suspenders in consumers: empty → skip tick; wrap with modulo of the CURRENT count; rate-limit the warn.

- **Static input gates leak across play sessions — reset them in OnStart AND OnDestroy.** `static bool IsOpen` style gates (EscapeMenu, CeremonyScreen) survive Play→Stop→Play within one editor process. A session ending with the gate set freezes the next session (character wouldn't move until the menu was toggled, resyncing the static). Rule: any static a gameplay loop reads must be hard-reset when its owning component spawns and cleared when it's destroyed. Grep `static bool` near input checks when adding UI overlays.

- **"Everything broke at once" after a burst of edits = check for a stale assembly FIRST.** When the package compile fails (an edit left mid-flight), the s&box editor silently keeps running the LAST GOOD hotloaded assembly — so a playtest can exhibit "regressions" from code that predates hours of committed work (audio dead, features missing). Before debugging any multi-symptom regression reported during a run of concurrent edits, grep the log for `Compile of ... Failed` / `Broken Reference` in the session window. If present, the fix is "finish/fix the broken edit + restart Play", not the symptoms.

- **Sounds/assets compiled AFTER a session started are invisible to that session — and a retry loop on them floods every frame.** The editor builds its asset registry at session start; .sound_c/.vsnd_c produced later (by another session, a background compile, or a git checkout) exist healthy on disk but "Couldn't find sound event" until an editor kick re-indexes. Two rules: (1) mtime staleness is a RED HERRING — prove it with a known-working control asset with identical mtimes before chasing it; (2) never per-frame-retry a failed loop: retry once after ~2s, then DISABLE with one warn (a permanently-invalid handle otherwise = one engine warning per frame per loop). A zero-volume canary probe of a few cross-bus events at first Sfx use turns "audio mysteriously dead" into one log line naming the editor kick.

- **The editor ignores external edits to persisted settings.json** - GameSettings caches its
 file read once per editor-process lifetime (`static bool _loaded`), so editing
 `data/local/<ident>/settings.json` on disk while the editor runs is silently ignored - a
 benchmark launched after flipping QualityPreset 0->2 externally still printed `preset=Low`.
 No stock ConVar flips quality in-process either. Headless preset changes need an in-game
 Video-tab click or a project `[ConVar]`-backed setter.

- **The engine ships its own built-in `[McpTool]`s as readable C# source, not just compiled
 DLLs — read it before inventing a pattern.** `<path> Files (x86)\Steam\steamapps\common\
 sbox\addons\tools\Code\Mcp\*.cs` (`Scene.cs`, `EditorTools.cs`, `AssetSystem.cs`, `Play.cs`,
 `Packages.cs`, `Log.cs`, `Components.cs`) is real source, ProjectReference'd (not just
 Reference'd) into every project's `.editor.csproj` — that's why it's on disk in full.
 one project's `Editor/SfxProbeTool.cs` (the usual "how to write a project [McpTool]"
 reference) is a pure resource-lookup tool and never touches the scene, so it can't show you
 the canonical "get the active editor scene" pattern — that lives in `Scene.cs`:
 `SceneEditorSession.Active?.Scene ?? Game.ActiveScene` (see `SceneTools.ResolveScene` /
 `ActiveSession`). Same file is also the reference for viewport screenshots
 (`Application.Editor?.Camera` + `camera.RenderToBitmap(bitmap, false)`), moving the editor
 camera (`SceneViewWidget.Current?.LastSelectedViewportWidget`), and resolving game objects by
 guid across every open `SceneEditorSession`. Read this before SfxProbeTool.cs for any new
 project [McpTool] that needs the scene, camera, or selection. Two attribute forms both
 compile: the house convention (SfxProbeTool.cs) is
 `[McpTool( "name", Hints = McpToolHints.ReadOnly )]`; the engine's own tools use the shorthand
 `[McpTool.ReadOnly( "name" )]`.

- **The editor MCP server's ENABLE is a MANUAL per-editor-instance Preferences step — a running
 editor may serve NO MCP at all — and the PORT is a single GLOBAL cookie persisted in
 `sbox/config/tools.json` as `McpServerPort`.** The enable state is still not automatable from
 code, so a freshly-launched editor serves nothing until toggled via Edit → Preferences → MCP
 Server. The cookie holds the last-set value across ALL editors, so switching projects may show a
 stale port — re-check before enabling. There is NO auto-increment past a taken port: the editor
 fails the bind and starts no MCP server, leaving a healthy editor with no MCP at all (log line
 under the `MCP` tag: `Couldn't start MCP server on port <port> (...)`; Preferences just shows
 "Not running", the same as disabled). Recovery: set a free port in Edit > Preferences > MCP
 Server (changing it restarts the server on the spot), or edit `tools.json` `McpServerPort` to a
 free port and relaunch. To find who's ACTUALLY serving, don't trust netstat's
 PID column (http.sys routes show PID 4): run `netsh http show servicestate view=requestq |
 findstr HTTP://` to list active listeners.

- **On a shared working tree, ONE uncompilable file reddens the WHOLE editor assembly and
 silently blocks every live MCP loop against that editor.** The s&box csproj is
 SDK-glob (no explicit `<Compile>` items), so it compiles every `.cs` under `Code/`; a
 half-written `UiRig.cs` referencing a not-yet-created `SessionMenu` failed the whole game
 `.csproj` (and, transitively, the `.editor.csproj`), which leaves the editor on a stale
 assembly with `compile_status` red for work that has nothing to do with that file. Judge only
 YOUR files by filtering the build output on path: `dotnet build … | grep ": error" |
 grep -v "<other-scope>"` (empty = yours are clean). Don't patch someone else's in-flight file
 to unblock yourself; wait for it to land, or revert it locally.

- **`editor_status` over the editor MCP can transiently return `Project: null` while
  mid-hotload** (right after a source change compiles). An identity-probing harness then
  aborts with a false "wrong port / wrong project" even though the port and project are
  correct. Fix: treat a null Project as "editor busy", wait ~10–15 s and re-probe before
  concluding wrong-port; only a different non-null project name means wrong port.

- **The editor MCP `camera_screenshot {includeUi:true}` captures base HUD panel elements fine
  but DROPS a centered full-screen modal card** — even one on the same ScreenPanel. The
  backdrop's dim/blur composites (the scene visibly dims) but the card and all its children
  never appear. This is a render-pass artifact of the modal sub-layer, not layout. Workaround:
  bind the asset-under-test to an always-visible base HUD element (which does composite),
  screenshot that, then revert.

- **Game code cannot subscribe to the engine log stream — `Sandbox.Diagnostics.Logging` is
  `internal`.** `Logging.OnMessage += handler` fails to compile (CS0234). Only
  `MenuUtility.AddLogger` / `EditorUtility.AddLogger` are public (menu/editor realm, not game).
  Workarounds: (1) derive events from observable side effects instead of log parsing; (2)
  bracket runs with grep-able START/DONE markers and have the outer tool grep the console
  between them.

- **When the whole HUD is gated behind a static flag on a static class, an MCP test harness
  that only pokes gameplay singletons can drive every gameplay verb yet capture ZERO HUD** —
  the flag never flips, the `@if` renders nothing, and screenshots show only the start menu.
  `set_component` reaches only component `[Property]` fields, never static class fields.
  Fix: expose the gate as a `[Property]` on a component, or skip HUD capture for automated
  runs and verify HUD separately.

- **The editor serializes its STALE in-memory `.sbproj` on any settings/wizard save, reverting
  on-disk hand-edits.** A `Resources` glob added by editing the file while the editor was open
  gets dropped without warning when the publish wizard runs. After any editor settings interaction,
  re-read the sbproj on disk and restore hand-edits (`git diff -- *.sbproj`). The publish wizard
  also PACKAGES from the stale in-memory copy — an editor restart (or editing through the Project
  Settings UI) is the only fix.

- **`editor_camera_screenshot` renders the EDITOR viewport (the edit scene), NOT the running play
  scene.** Anything that exists only at runtime (procedurally generated terrain, play-mode-spawned
  objects) is invisible to it. Capture the play scene with the `scene` toolset's
  `camera_screenshot` instead (arg = a CameraComponent/GameObject id, or omit for the scene's
  main camera).

- **A newly added Component type can be compiled-but-not-yet-registered in the TypeLibrary
  right after the editor loads the assembly.** `compile_status` is green but playing a scene that
  references it logs `TypeLibrary could not find <Type>` and silently skips the component (its
  `OnStart` never runs). Resolves on its own after a short window. Gate: re-query
  `get_component_type` before concluding the component is broken; if it now resolves, reboot play.

- **The editor MCP resolves only ONE component per GameObject.** `set_component {type}` fails on
  any secondary component with `has no <Type> component`. Workaround: drive behavior through the
  component you CAN reach, or put the thing you need to script on its own single-component
  GameObject.

- **Compiling AND loading hundreds of runtime-written vmdls in one warm editor session can exhaust the resource-stream VM and CRASH the editor: `CResourceStreamVM::Commit: Failed trying to Commit 65536 bytes, used 0 bytes, reserved 67108864 bytes`.** A world exporter baked ~900 land + ~418 water per-chunk vmdls, `AssetSystem.RegisterFile`'d them all (which compiled fine), then **cloned the full 1318-child prefab — loading every compiled model at once** — and the editor died on the resource commit. The crash is on the render/STREAM commit, not the file write or the compile. Mitigations: (1) spawn/load in SMALL batches (≤ 6–9 models) with brief waits — 6-at-a-time loaded 36 chunks with zero pressure; (2) for a visual check spawn only a contiguous central block (~25–36 chunks), never the whole world; (3) for a genuine full-world bring-up use a FRESH session (restart between the bake and the mass load) so pressure resets. Note the global MCP-server port moves on the crash/restart — re-identity-probe before the next call.

- **A green `compile_status` (and green headless `dotnet build`) can coexist with a STALE play-mode hotload that reports errors for symbols/lines which no longer exist in source.** After a burst of edits that removed a type member (deleted `CarDefinition.BodyModel`/`HatchFused`), `play_start` spewed recurring `Warn: Error | 'CarDefinition' does not contain a definition for 'BodyModel' - VehicleFactory.cs:402,41` and the default spawn silently failed — yet the editor's authoritative `compile_status` showed all compilers Success=true/0 errors AND `dotnet build` was green AND the on-disk file had none of those lines. The play-mode hotloader had compiled an intermediate/cached snapshot from mid-edit (the reported line numbers kept SHIFTING across boots as it caught different stale states). Two ways to tell it apart from a real failure: (1) the offending errors are BUFFERED in `read_console` with OLD timestamps — filter by time and look for the post-recompile SUCCESS log (a project line such as `partkit '<kit>' body assembled: N/N`) to confirm the live assembly is current; (2) force a clean re-read by `os.utime`/`touch` on the edited `.cs` files, wait ~8-12 s for the `IsBuilding` cycle, re-check `compile_status`, THEN re-boot — the stale errors stop and the spawn works. Corollary: deleting compiled `_c` assets (sounds here) out from under a LIVE editor emits one-time `Detected Asset File Deleted` + `Cannot recompile: Source file not present` + `ERROR_FILEOPEN` warnings as the watcher drops them from the index; these SELF-HEAL and do not recur on later boots — not a regression.

- **CORRECTED (was: "the `.archetype` extension is engine-reserved" — that theory was wrong; the real rule is a hard 8-CHARACTER CAP on custom GameResource extensions).** A custom GameResource with `[AssetType(Extension = "archetype")]` (9 chars) can never compile its assets: every file fails with "can't be recompiled - it has no source file (cloud and compiled-only assets can't compile)" while an identically-formatted sibling GameResource type compiles fine. It is NOT about the word "archetype" — a second attempt at `.charclass` (also 9 chars) failed the SAME way, and renaming to `.charcls` (7 chars) fixed it immediately (`asset_compile` Success, a real `_c` produced). **Rule: custom GameResource file extensions must be ≤8 lowercase characters, or the type silently never registers as a compilable SOURCE type.** Mechanism (two enforcement points, both length-based, neither name-based): (1) the obsolete `[GameResource]` attribute actively enforces this — `engine/Sandbox.Engine/Resources/GameResourceAttribute.cs:120-124` logs an error and TRUNCATES the extension to 8 chars; (2) the modern `[AssetType]` attribute (see `g-ui-gameresource-attribute-obsolete-use-assettype`) sets `Extension` via a plain property with **no validation at all**, and passes it straight to the native `IAssetSystem.UpdateGameResourceType` (`Sandbox.Tools/Assets/AssetType.cs:355`) — an over-length extension there just silently never registers as a compilable source type, no error, no truncation. That's why the symptom is misleading: the asset shows the right TYPE in listings, but `asset_compile` fails with the "no source file" message above, and an on-demand recompile emits no `_c` at all (console shows a `recompile` Info line then `ERROR_FILEOPEN` loading the missing `_c`). A second 8-char check lives at `GameResourceProcessor.cs:34`, which rejects asset-REFERENCE paths (not just the type extension) longer than 8 chars. Facepunch's own docs (sbox-docs `docs/assets/resources/custom-assets.md`) state the filetype must be all-lowercase and ≤8 characters "otherwise it will fail to register/save" — every first-party extension complies by abbreviating (`sndscape`, `tmat`, `clthgrp`). "archetype" DOES appear in the engine, but only as `ModelArchetype`, an unrelated ModelDoc/Hammer enum (`engine/Sandbox.Engine/Editor/Hammer/HammerAttributes.cs:10`) — there is no file-extension reservation of the word anywhere; a shorter synonym containing "archetype"-adjacent meaning would have failed identically at 9+ chars. Fix: keep any custom GameResource extension to 8 lowercase chars or fewer (moved to `charcls`) — don't grep the engine for your candidate WORD, count its LENGTH.

- **Hotloading does NOT unregister a `[AssetType]`/`GameResource` type registration — renaming a resource's extension and hotloading leaves the OLD extension registered ALONGSIDE the new one until the editor fully restarts.** After moving a GameResource from `Extension = "archetype"` to `"charcls"` (see `g-tool-gameresource-archetype-extension-reserved`) and hotloading, the editor's asset-type listing showed a DUPLICATE type entry carrying both `["archetype", "charclass"]` — the stale registration wasn't replaced or removed, just shadowed. A full editor restart cleared it back to the single correct entry. This is a red-herring generator when debugging resource issues: after renaming/removing an `[AssetType]` extension, don't trust the live editor's registered-types list (or any tool that reads it) until you've restarted — a hotload-only check can show the old extension as still "registered" when it's actually dead weight from before the rename.

- **Run exactly ONE s&box editor per project, on its assigned MCP port — and verify a port's IDENTITY by its scenes/toolset, not by a project-name probe.** When `list_scenes` persistently disagrees with what the editor window actually shows, the cause is usually a second editor: the MCP identity probe can't disambiguate (two instances of the same project report the same Project), and a stale/second instance answers on a different port. Concretely (2026-07-12): the target project's port 7269 was DOWN while two other editors were live — 7290 (a sibling project, identified by its own scene name) and 7200 (a third project, identified by its own tool-name prefix). Detect with `Get-NetTCPConnection -State Listen` over the port range + `list_scenes`/`search_tools` on each reachable port to read its real identity; NEVER `play_start` a port you haven't identified (you could drive the wrong project's scene). If the target editor isn't up, do all headless work + commit, and leave the in-editor steps written down as a runbook to walk through by hand.

- **Driving the s&box editor over MCP in an edit -> regenerate -> screenshot loop silently renders the PREVIOUS assembly: successful hot-compiles log NOTHING to the console (only failures print "Compile of ... Failed"), and `compile_status` reports the LAST completed build — so it can read green while your newest .cs save is still queued or was never picked up.** Symptom: the "after" screenshot is pixel-identical to the "before" and you chase a phantom non-fix (or worse, a transient mid-edit compile FAILURE leaves the last-good assembly live and green-looking). Protocol that held up: after the last file write, poll `compile_status` until `IsBuilding=false` AND `NeedsBuild=false` AND `Success=true` for BOTH local.<project> and local.<project>.editor, sustained across ~3 polls / >=12 s, and check the console for "Failed" lines timestamped after your write — only then regenerate. Multi-file edit bursts also trigger genuine transient failures per intermediate save; they are noise, but the LAST compile must postdate the LAST write. A `touch` on the file re-arms the watcher if it missed a save.

- **If the editor is IN PLAY MODE, `camera_screenshot` renders the PLAY session's scene clone (frozen at whatever the world was when play started) while world/grid tools keep rebuilding the EDIT scene — so every "after" screenshot silently shows a world from N regenerations ago.** Symptom cascade observed: two different-style regenerations produced pixel-identical screenshots; a probe shot matched a style generated 20 minutes earlier; `delete_game_object` on the world root did not change the render (it deleted the play clone's root); scene queries showed 1 clean world root (the play scene's). The tell: `play_start` errors "Already playing" / `editor_status.IsPlaying == true`. Play mode can be entered outside your control (someone at the keyboard, a leftover test session), so an MCP evidence loop must CHECK `editor_status.IsPlaying` before generate-and-screenshot evidence passes and `play_stop` (or report) if unexpected. Edit-scene state survives play/stop; in-play scene edits are discarded on stop. **Write-side corollary (MCP capture session, engine 26.07.22): an MCP scene edit made WHILE PLAYING lands on the EDIT scene, not the play clone that's actually rendering, so the edit has zero visible effect until the next `play_start`** — e.g. repositioning a capture camera by adjusting the camera-driving component's transform mid-play never moves the running (frozen-clone) view, because the edit lands on the dormant edit-scene copy of that GameObject, with no error to say so. Reliable recipe for repositioning a capture camera: `play_stop` first, adjust the camera-driving component and set the transform on the now-live EDIT scene, then `play_start` and capture. **Not universal, though (same build, second capture session): MCP scene edits to moving lights and to ground-plane objects DID affect the running play-clone live, no `play_stop`/`play_start` needed — so which scene an in-play MCP edit lands on is INCONSISTENT across object/component types (camera-driving component → dormant edit scene; lights + ground objects → live play clone). Don't assume either behavior going in: read back the running scene's actual state after any in-play MCP write before trusting it. The stop-edit-start recipe above stays reliable specifically for camera work.**

- **Lambdas stored in a STATIC collection get error-delegated on hotload — invoking one throws `NotImplementedException: Unable to find matching substitution for a lambda method` (`__error_delegate<NoMatchLambda>`), and because the static ctor does NOT re-run on hotload it stays broken for the whole editor session.** a project's `Buildables.All` holds `Action<GameObject> Attach` lambdas (`go => go.Components.Create<CropPlot>`). Editing Buildables.cs hotloaded and the editor log showed `[hotload/GameMenu] Warn: Unable to find matching substitution for a lambda method... Buildables::All[].Attach` + `Unable to find scope method (Name:.cctor, Ordinal: 4)`. Every spawn of a lambda-attached buildable (garden_bed -> CropPlot) then throws at `def.Attach.Invoke(go)` inside `Buildables.Spawn` — this is GAME-WIDE (BuildSystem.Place, SaveSystem load), not just the MCP path. Tell-tale: a buildable with NO Attach (fence/gate) spawns fine; a plain method call or a direct `go.Components.Create<T>` is fine — only the STORED delegate is stale. FIX (two levels): (1) a fresh editor restart re-runs the static ctor -> valid lambdas; (2) for a test harness that ALWAYS runs post-hotload, don't invoke the catalog lambda at all — add a `runAttach` flag so the tool spawns bare (`runAttach:false`) and re-attaches the domain component with a direct `Components.Create<T>` at the call site (JIT-resolved, never a stale delegate). Design lesson: prefer a switch/type-dispatch over lambdas stored in a static catalog if the path must survive hotload. (build-tool slice, 2026-07-12) UPDATE 2026-07-17 (TweakDials.All, dial Get/Set lambdas — the K tweak panel died session-wide with per-frame `Error calculating hash on <PanelComponent>... Unable to find matching substitution for a lambda method` warn spam after live-editing the dial table): fix level (3) — **`[SkipHotload]` on the static catalog field** makes every hotload skip the stale-value migration and re-run the initializer → fresh, valid lambdas, so the catalog survives live edits. Only safe when the catalog is STATELESS (rebuilt-from-code, e.g. dial rows reading/writing ConVar statics); state you want preserved must live in separate non-skipped statics. Already-wedged sessions still need the editor restart.

- **The s&box editor fires a one-time scene HOT-RELOAD ~15-20 s into a fresh Play session, which re-runs the scene bootstrap (rebuilds the world, RESPAWNS the player) and ORPHANS any suite that was armed by a console convar** — the fresh component instances start Idle, and a convar-armed-on-rising-edge suite never re-arms because the convar is already set (no new edge), so it wedges partway with the body frozen and no error. Symptom seen live: a scripted suite consistently stalled right after the 5th metric, with "<pilot> attached" logged 3x + a character respawned at the spawn pad mid-run. WORKAROUND for a clean capture: play_start -> arm -> let the reload fire (~24 s) -> RE-ARM by toggling the convar 0 then 1 -> the re-armed suite runs to completion. It is an editor/session artefact (the very first post-build run and the shorter smoke suite both complete clean), not a harness or gameplay bug.

- **A STRUCTURAL `.razor` change (added markup/fields shifting the generated class + its `b__NN` lambda ordinals) can throw a live-editor HOTLOAD EXCEPTION that DEREGISTERS the whole project `[McpTool]` toolset while `compile_status` still reads Success=true - recover by RESTARTING the editor, not by more file edits.** Seen live (engine 26.07.08e): mid-edit the editor logged `[hotload/GameMenu] Error: Unable to resolve method definition ... <PanelType>.<RowMethod>b__74_0` + `Hotload exception`; afterwards `editor_status.ToolCount` dropped by exactly the project's tool count (the game assembly's failed hotload left the dependent `.editor` assembly unloaded, so every project tool answered `Unknown tool '...'`), yet `compile_status` reported `local.<project>` AND `local.<project>.editor` Success=true, NeedsBuild=false. DIFFERENT from the success=False compiler-wedge - here the COMPILE succeeded and the whitelist verdict is still trustworthy (Success=true, 0 SB1000 = the APIs passed), but the RUNTIME assembly swap failed. Neither `touch`, content edits, nor `console_command compile`/`hotload` (both `Unknown Command`) re-registered the tools - `NeedsBuild` stayed false. The only fix is an editor restart, which no MCP call can do for you: finish the headless work, commit, then restart the editor in its own window. Detect: `ToolCount` below the known-good number + `Unknown tool` on a tool that compiled clean. Minimize risk by not editing many `.razor` files against a LIVE editor in one burst. Companion: when the trigger was a **failed** compile (not a hotload exception after Success), see `g-tool-failed-compile-empties-typelibrary-missingcomponent`.

- **A failed in-editor compile of the game package empties TypeLibrary for project types — Play can still "start", but scene components become `MissingComponent` and the game never boots; `compile_status` may later lie Success=true while ToolCount stays at the stock editor-only count.** Observed 2026-07-14: razor `CS1501` (`HashCode.Combine` 9 args in a HUD panel) failed `local.<project>` → editor package Broken Reference → session never re-loaded game/editor assemblies. Symptoms: (1) console `Missing Component: couldn't find Component type <Project>.GameBootstrap on GameObject:Game`; (2) `find_game_objects` shows `Components: ["MissingComponent"]` even though on-disk `.scene` still has the real `__type`; (3) `get_component_type` / `add_component` for project types fail ("No component type matches"); (4) `search_tools <project-tool-prefix>` → 0 hits, `ToolCount` stuck at stock (~52) instead of known-good (~57); (5) no project boot log line after `play_start`. Headless `dotnet build` going green does NOT repopulate TypeLibrary. **DO NOT save the scene** while MissingComponent is showing — that would bake the strip into the asset; the on-disk file is still good (same law as `g-tool-steam-update-s-box-engine-underneath`). Recovery: fix the compile error on disk → **restart/reopen the editor** (no MCP recompile/reload tool exists) → confirm ToolCount / project tools / `get_component_type` before Play. Related wedge after a *successful* compile + failed hotload swap: `g-tool-structural-razor-edit-hotload-wedge-deregisters-toolset`.

- **The s&box editor PRESERVES static fields across a code hot-reload**, so any static CACHE goes stale when its backing DATA changes out-of-band and is never re-read until a full editor restart.
