## Tooling (see tooling.md for detail)

- **PowerShell 5.1 corrupts UTF-8 on bulk edits** (`Get-Content`/`Set-Content` reads
 BOM-less UTF-8 as ANSI → emoji/dash mojibake). Use python or byte-safe .NET file APIs.

- **Some C# source files in one project are CRLF, and a `\n`-based string-replace edit
 silently fails to match them** (the search string has `\n`, the file has `\r\n`, so the
 multi-line `old_string` never hits — the byte content otherwise looks identical under
 `od -c` per-line, which hides the `\r`). Symptom: an exact-looking edit reports "string
 not found" repeatedly on a block you can see in the file. Diagnose with
 `python -c "print(b'\r\n' in open(p,'rb').read)"`; fix by editing via a python
 byte-level `data.replace(old_bytes, new_bytes)` with `\r\n` in the literals (assert the
 match count is 1 first), then write back `'wb'`. Mixed in the same repo — ProjectileTuning.cs
 is CRLF, ProjectileSplat.cs is LF — so check per file.

- Verify compiles without the editor: `dotnet build Code/<proj>.csproj` — the csproj
 references the Steam s&box install directly. Do this after every batch of edits.

- **A stalled Steam update half-deletes the s&box install — close the launcher.** If
 `sbox-launcher.exe` stays running across an update (e.g. left open overnight), Steam
 downloads + stages the update but can't commit while files are in use, and the install
 ends up missing files: `sbox-dev.exe` gone (launcher's "open project" silently fails —
 no window, error only in `sbox/logs/sbox-launcher.log`), random dlls gone
 (`Sandbox.CodeUpgrader.dll` → all headless `dotnet build`s fail with CS0006 from
 `Base Library.csproj`). Diagnose: `steamapps/appmanifest_590830.acf` StateFlags ≠ 4
 with 100% BytesStaged. Fix: kill the launcher, run `steam://validate/590830`, wait for
 StateFlags 4. Don't "fix" the csprojs — they were never broken.

- **`dotnet build` warning counts lie under incremental builds** — warnings are only
 re-emitted for files that actually recompile, so a stale-output build happily prints
 `0 Warning(s)` over a tree that carries warnings. Any build-gate claim (docs,
 feature-matrix headers, agent verify clauses) must come from
 `dotnet build --no-incremental` (or a clean). Per-agent scope checks can stay
 incremental — it's the WHOLE-TREE 0/0 claims that need the rebuild.

- **Steam can update the s&box engine UNDERNEATH a running editor** — files swap mid-session
 and the symptoms look like impossible compiler bugs, in escalating order (observed 2026-07-10,
 26.07.08c->e): hotload "Failed to clean" reflection noise -> an internal Roslyn NRE
 (`GetExtensionContainers`) wedging the compiler (success=False, 0 diagnostics) -> on restart,
 `SerializationDeprecationException` + "Errors when loading 'Sandbox.Project'" (mixed-version
 DLLs), the scene deserializing with project components STRIPPED (MissingComponent — do NOT
 save the scene in that state, the on-disk file is still good), the package never mounting
 (type registry empty, nothing plays) -> "Could not find sbox-dev.exe" if relaunched while
 Steam stages that exact file. FIRST CHECK for any inexplicable editor-internal crash:
 `sbox/.version` mtime vs your session start (also `appmanifest_590830.acf` StateFlags —
 4 + all BytesStaged = update complete). Recovery once the update finishes: relaunch, discard
 scene changes, verify headless `dotnet build --no-incremental` against the NEW engine
 assemblies before trusting anything.

- **s&box whitelist is only enforced by the IN-EDITOR compiler** - `dotnet build` passes code that the game runtime then rejects (e.g. `Environment.TickCount` -> SB1000 whitelist violation). Fix: engine surfaces only (`Time.Now`-derived entropy for seeds, `System.Random(int)` itself IS whitelisted). Sweep agent code for `Environment.*`, `System.IO`, `Process`, `Thread` before shipping.

- **Runtime reflection is ALSO whitelist-banned** in s&box game code - `Type.GetProperty`/`PropertyInfo.SetValue` -> SB1000, same as `Environment.*`. Never use reflection as a cross-file workaround for a property another agent owns; emit a HANDOFF instead.

- **.sbproj `Org` must be a valid lowercase package ident — a placeholder breaks engine BOOTSTRAP, not just publishing.** Setting Org to an uppercase TODO string made `Sandbox.PackageLoader.LoadAssemblyFromPackage` assert at editor startup ("File doesn't exist? Maybe a case sensitivity issue??") — the whole editor fails to boot, which reads as engine corruption, not a config typo. Keep `local` for dev; set the real org only when it exists, and never park a non-ident placeholder in that field (document the TODO in a doc instead).

- **Adding a `public` method to the GAME assembly and calling it from the EDITOR-tools
  assembly in the SAME hot-reload pass throws `MissingMethodException`** — even though
  `compile_status` is all-green and `dotnet build` is 0/0. The running editor assembly
  re-JIT'd against a stale copy of the game assembly that predated the new method. Fix:
  restart Play (a fresh Play session loads both assemblies together); the exception is
  transient to the cross-assembly hot-reload seam only.

- **`Array.Clone()` is NOT whitelisted in the game assembly** — `(short[])arr.Clone()`
  compiles headlessly but fails the in-editor compile with `SB1000 'System.Array.Clone()' is
  not allowed when whitelist is enabled`. The old assembly silently keeps running. Fix: use
  `var copy = new short[a.Length]; System.Array.Copy(a, copy, a.Length);` — `Array.Copy` IS
  whitelisted. Always check `compile_status` after a game-assembly edit.

- **The `FileSystem.Data` multi-file API surface is whitelist-clean and works at runtime for
  a named-slot save system:** `WriteAllText`, `ReadAllText`, `FileExists`, `DeleteFile`,
  `DirectoryExists`, `CreateDirectory`, `FindFile(dir, "*.json")` all compile in-editor AND
  execute. Paths are relative to the project data root; sub-dirs like `saves/<slug>.json`
  work. Sanitize any user-derived slug (drop `/ \ .`) to prevent path traversal.

- **On Windows, invoking `python3` from a project tool aborts with exit 49** ("Python
  was not found; run without arguments to install from the Microsoft Store") even though
  Python is installed and on PATH — `python3` resolves to the WindowsApps App Execution
  Alias shim, not the real interpreter. Use `python` or the launcher `py` instead.

- **Porting a `.cs` file into another s&box project with its doc comments intact: a
  `<see cref="TypeYouDidNotCopy"/>` in an XML `///` comment emits CS1574** ("XML comment
  has cref attribute that could not be resolved") — which quietly fails a "0 warnings"
  acceptance gate even though the code is correct. For a small port: grep for `cref=`
  and strip or redirect references to types you didn't copy. For a LARGE vendored
  slice you want to keep drift-diffable against upstream: prepend
  `#pragma warning disable 1574` to each vendored file instead of scrubbing the
  crefs — keeps bodies byte-identical to the source for drift-sync.

- **Moving legacy assets out of a publish payload with `git mv` alone leaves the shipped bytes
  behind AND a source-only dependency closure misses shared textures.** Compiled artifacts
  (`*_c`, `*.generated.*`) are git-ignored, so `git mv` only relocates sources. AND a
  `.vmat`/`.vmdl`-only move misses shared `.vtex` files referenced by the material. Combine
  the `git mv` with a `git rm` of the compiled artifacts and trace the full texture closure.

- **Git worktree at a different directory depth breaks sbox csproj relative refs** — the generated `.csproj` uses deep `../` paths that only resolve at the main checkout's depth. Build from a worktree-local `.csproj` with absolute paths. The throwaway csproj can also execute pure logic headlessly (catches real runtime crashes like `ArgumentException` in date parsing before the in-editor gate) — but it validates neither SCSS nor the whitelist. Delete temp csproj + obj before finishing.

- **s&box DOES ship a first-class headless dedicated server, and it can run an UNPUBLISHED local `.sbproj` — no sbox.game publish required.** It's a separate Steam app (**`1892930`** — the client is `590830`), installed via SteamCMD with **anonymous login** and launched headless (no GPU/render window) with `sbox-server.exe +game <ident|C:/path/to/proj.sbproj> +hostname <name> [+net_game_server_token <tok>] [+port +net_query_port]`. Pointing `+game` at a **local `.sbproj` path** makes connecting clients stream+hotload the project's code/assets straight from the server — the sanctioned dev/iteration path (also the only supported way to run server-only code, since published sbox.game packages have server code stripped). Discovery is via **Steam lobbies / the multiplayer UI, NOT a paste-an-IP browser**; the dedicated server surfaces to clients when `Networking.QueryLobbies(filters, includeServers:true, ct)` is called with `includeServers = true` (the bool most lobby code leaves `false`), then `Connect(id)` joins it. TRAPS: (1) refresh SteamCMD's app metadata before choosing a branch: `+app_info_update 1 +app_info_print 1892930`. On 2026-07-12 the first public install attempt returned `Missing configuration`, while staging installed 3.28 GB and booted successfully as server `26.07.12`; after the metadata refresh, public installed successfully as `26.07.08e`, exactly matching the installed client. Prefer the matching branch — a staging server + public client discovered each other but the client then failed loading `local.`. (2) `+game <path.sbproj>` LOADS the project but does NOT activate `Networking`: the game must call `Networking.CreateLobby` itself (or it silently runs a headless single-player world). A dedicated process cannot call `Networking.QueryLobbies` (`unable to query lobbies on a dedicated server`), so its host path must skip short-code collision searches and create/advertise directly. (3) Steam drops custom `Networking.SetData` when aggregate game tags exceed **128 characters** — live log: `Steam game tags exceed 128 char limit ... Data dropped`; use tiny discovery metadata such as `g=gb,p=1,d=1`. (4) The older public build was documented STALE (Nov-2023 `.version`, didn't recognise `+game`) in Facepunch/sbox-public issue #3356, so always compare `.version` to clients. (5) `net_game_server_token` (persistent
 server Steam ID) is documented as available "once the game is publicly released" — whether a
 local/unpublished (`Org: local`) project gets a usable token + shows up in discovery is UNVERIFIED,
 test before relying on it. Do NOT trust nexus-games-style guides using `sv_tickrate`/`dm_crossfire`/ `workshop.txt` — those are Garry's Mod/Source-1 and don't apply to s&box.

- **`[GameResource]` and `NavMesh.GetSimplePath` are `[Obsolete]` (CS0618) on engine 26.07 — a zero-warnings build gate fails on both.** Modern replacements, each compiles clean: (1) mark a `GameResource` subclass with **`[AssetType(Name = "...", Extension = "npc", Category = "...")]`** instead of `[GameResource("title", "ext", "desc", Icon = "...")]` — `GameResourceAttribute` now derives from `AssetTypeAttribute` and is deprecated; `AssetType` exposes `Name`/`Extension`/ `Category`/`IconColor`/`Flags` (there is NO `Description` or `Icon` ctor arg — drop them). The base class stays `: GameResource`. (2) Replace `scene.NavMesh.GetSimplePath(from, to)` (returned a `List<Vector3>`) with **`scene.NavMesh.CalculatePath(new Sandbox.Navigation.CalculatePathRequest { Start = from, Target = to })`** → returns a `NavMeshPath` struct with `.IsValid` + `.Points`, an `IReadOnlyList<NavMeshPathPoint>` where each point exposes a `.Position` (Vector3) — it is NOT a `List<Vector3>`, so index `path.Points[i].Position`. Related surface that is NOT deprecated: `Scene.NavMesh.IsEnabled` (gates whether a baked navmesh exists — the scene default is disabled), and `GetRandomPoint(pos, radius)` / `GetClosestPoint(pos, radius)` returning `Vector3?`. Found via offline metadata reflection (MetadataLoadContext over bin/managed) when building headless. → [fix article](/fix/gameresource-navmesh-getsimplepath-obsolete)

- **'s `WorldGen.Regenerate(Scene, WorldSpec)` really is a drop-in static library for another sbox project — the whole Code/Gen + Code/Mesh + WorldSpec/Tuning/ set copied into and built 0/0 after severing exactly THREE code-level deps and a global-namespace rename.** Verified reuse recipe: (1) the wb Gen/Mesh/Game files are all GLOBAL namespace (no `namespace` decl); the destination project mixed a `` namespace with many global-namespace files, so generic copied type names share the global namespace and can collide — grep the destination for every copied top-level class name first (here: no literal collisions, but `Tuning`/`Noise` are landmines), then whole-word rename the collision-prone ones (`Tuning`→``, `Noise`→``) rather than wrapping in a namespace, so the bodies stay 1:1 re-diffable against wb. (3) The FNV-1a grid-hash determinism probe (.GridHash, grid arrays + dims only, NO scene reads) ports straight across and is the one-line determinism proof: two `Regenerate` calls of the same seed on the ACTIVE play scene logged byte-identical `hash=7c74aee7accee1fe` (100 chunks / 101244 tris) either side of a clear. Bake the material-path strings into a const pointing at the copied `Assets/materials/<dst>/` (2 live: terrain atlas + water; the sky path is dead once is dropped).

- **`git worktree add` gives a headless `dotnet build` nothing to build — the `.csproj` files are gitignored (`*.csproj` in `.gitignore`, s&box regenerates them from the editor), so a fresh worktree's `Code/`/`Editor/` folders have no project file at all.** `dotnet build Code\.csproj` fails `MSB1009: Project file does not exist` even though the exact same command works in the main tree. Fix: copy the two `.csproj` files from the main working tree into the worktree before building — they are boilerplate SDK-style projects with `../../../../../../../Program Files (x86)/Steam/steamapps/ common/sbox/...`-relative references, so the copy resolves correctly as long as the worktree sits at the SAME path depth as the main tree (e.g. `dev/<project>//Code/` and `dev/<project>/wt-<slug>/Code/` are both 4 segments under `dev/`, so the relative reference count matches). Never commit the copied `.csproj` (still gitignored; verify with `git status` after copying). **If the worktree sits at a DIFFERENT (deeper) depth** — e.g. a scratch worktree under `.claude/scratch/worktrees/<slug>/Code/` — the relative `../…/Steam/...` refs resolve to the wrong root and the copied csproj fails to find the s&box DLLs; instead author a worktree-local `.csproj` with ABSOLUTE `C:/Program Files (x86)/Steam/steamapps/common/sbox/...` Reference/Analyzer/ ProjectReference paths (depth-independent). Also redirect `<OutputPath>` + `<DocumentationFile>` to an isolated in-worktree folder: the stock csproj writes to the SHARED `sbox/.vs/output/`, which the live editor uses — a verify build must not clobber it. Do NOT point `<BaseIntermediateOutputPath>` at a custom folder (warns MSB3539, and stale generated `*.AssemblyInfo.cs`/`AssemblyAttributes.cs` left under it get globbed into the compile → a wall of `CS0579` duplicate-attribute errors); leave `obj/` at its default (the SDK auto-excludes it from the compile glob) and `rm -rf` any stray intermediate/output dir before rebuilding. **With the isolated custom `<OutputPath>`, a second build run with `--no-incremental` can FAIL `MSB3030` ("Could not copy … deps.json / staticwebassets. endpoints.json … not found")** — the Razor SDK's `--no-incremental` clears the output then the copy-outputs step races the just-cleared isolated dir. It is a stale-state flake, not a code error: the FIRST build (or a plain `dotnet build` with NO `--no-incremental`) succeeds. Fix: `rm -rf` the custom output + `obj/` and run `dotnet build` WITHOUT `--no-incremental`; prefer a clean+plain build over `--no-incremental` for a deeper worktree with a redirected OutputPath. **Addendum:** the full recipe that held up on a live worktree build also replaces every `ProjectReference` pointing OUTSIDE the worktree (most commonly `addons/base/code/Base Library.csproj`, and any vendored Library project) with a plain `<Reference>` HintPath'd at its prebuilt DLL under the main tree's build-output folder — a worktree build has no business recompiling code it isn't changing, and a `ProjectReference` resolves that project's output into the same shared folder the live editor compiles into. → [fix article](/fix/git-worktree-missing-gitignored-csproj)

- **Vendoring a GLOBAL-namespace code slice into another project? Wrap the WHOLE slice in ONE sub-namespace — don't play per-type rename whack-a-mole.** 's generation code lives in the global namespace, where its `Noise` class collides with `Sandbox.Noise` once `global using Sandbox;` is in scope (the M5 copy solved this by renaming `Noise→`, `Tuning→` per-type). Vendoring the same slice into (B1), a cleaner move: prepend `namespace .Wb;` to every copied file (a mechanical byte-safe pass). All cross-file references resolve within the namespace unchanged; the one `using static ;` becomes `using static .Wb.;` (a using directive sits OUTSIDE the file-scoped namespace, so it needs the full path). Result: collision-proof by construction, zero per-type renames, and the vendored slice is quarantined from the consumer's own types. Headless build AND in-editor whitelist both 0/0. ( B1, Code/Wb/)

- **In an Editor-assembly type (an `[McpTool]`, `[Menu]`, etc.), a bare `FileSystem` is a CS0104 ambiguity between `Editor.FileSystem` and `Sandbox.FileSystem` — and headless `dotnet build` of the GAME csproj never sees it, because the editor assembly is compiled only in-editor.** A tool that read `FileSystem.Mounted.ReadAllText(path)` built green headlessly (0/0) but the in-editor `compile_status` reported 2× CS0104 on the `local.<project>.editor` compiler. Fix: fully-qualify `Sandbox.FileSystem.Mounted` (the mounted game content) — `Editor.FileSystem` is the editor's own FS and is almost never what you want. Broader rule this reinforces: for ANY code in the Editor assembly, the authority is the in-editor `compile_status`, not `dotnet build proj` (which compiles only the game assembly). Poll `compile_status` after the edit and inspect the per-compiler `Success/Errors` for the `.editor` compiler specifically.

- **On a Windows OpenSSH server, an admin user's public key placed in ` may be SILENTLY IGNORED -- Windows' default `sshd_config` ships a `Match Group administrators` block that redirects admin-group keys to ` and sshd reads that file ONLY if its ACL is SYSTEM + Administrators with inheritance stripped.** Before installing a key for an admin account, check which regime the box is in: `Select-String 'administrators_authorized_keys' If that Match block is UNcommented (the default), write the key to the ProgramData file and lock it down: `icacls <file> /inheritance:r /grant Administrators:F SYSTEM:F`. If it is commented out (seen on some provisioned boxes), the normal user path `~/.ssh/authorized_keys` works (still set the strict ACL). Do NOT edit `sshd_config` to "fix" it -- that requires an `sshd` service restart, which is off-limits on a shared production box. Verified 2026-07-15 on a Windows Server 2022 box whose Match block was commented, so the user path worked.

- **A long-running process (e.g. a dedicated game server) started over a Windows OpenSSH session is KILLED the moment the ssh session closes -- `ssh box "start-server.bat"` looks like it worked, but the server dies as soon as the command returns.** sshd tears down the session's child processes on disconnect, and `Start-Process`/`-WindowStyle Hidden` does not escape it. Verified 2026-07-15 (Windows Server 2022, sbox-server.exe): the process was alive when probed from INSIDE the launching session (8 s in), and gone (`Get-Process` count 0) from a new session immediately after the first closed -- which also silently invalidated an earlier "guard didn't refuse" test result (the process the guard was supposed to detect was already dead, not missed). Two consequences: (1) the launch path for a live server on a remote Windows box is a SCHEDULED TASK (or service) -- task-launched processes are not tied to any ssh session; a flag-file-armed watchdog task that relaunches the server if it exits covers both boot and crash-recovery. (2) When TESTING anything against a "running" server over ssh, keep the launch, the test, and the assertion in ONE ssh session, or the server will be dead before the test runs.

- **In a SHARED multi-agent working tree, `dotnet build` as a personal verification gate fails on OTHER agents' uncommitted/untracked WIP that doesn't compile — their broken files break your build, even though your own changes are fine.** Confirmed independently by two agents on the same day (, 2026-07-15). Working recovery both converged on: `git worktree add --detach <path> HEAD` (or a clean `main`), copy in ONLY your own changed files, build there in isolation. Two s&box-specific traps in that recovery: (1) the worktree MUST sit at the SAME directory depth as the original repo clone — the editor-generated `.csproj` references the Steam s&box install via long relative paths (`../../../../../../…`) that only resolve at that depth, so a worktree created shallower or deeper breaks the reference; (2) that `.csproj` is gitignored (editor-generated, not tracked), so `git worktree add` does NOT bring it along — copy it in by hand too. Alternative to depth-matching: rewrite the copied `.csproj`'s relative paths to absolute paths instead (one agent did this and it also worked).

- **A `set`-only `[ConVar]` property (no getter) breaks the s&box ConVar source generator with a PHANTOM `CS0019` — "Operator '??=' cannot be applied to operands of type 'Func<int>' and 'lambda expression'" — attributed to the WRONG line in your file** (the generated-code mapping, tens of lines off from your property; the cited line contains no such code). Invisible to headless `dotnet build` (the generator runs only in the editor compile), so `dotnet build` is GREEN while the in-editor `compile_status` FAILs — the "editor is the whitelist authority" gate biting via the source generator, not the whitelist itself. Fix: give the ConVar property a getter backed by a field (`get => _arg; set { _arg = value; ... }`), like every other ConVar in the codebase.

- **A fresh `git worktree` of an s&box project cannot `dotnet build`: the editor-generated is GITIGNORED (so the worktree doesn't have it), and a straight copy from the main tree still fails because the csproj references the Steam engine DLLs via RELATIVE paths computed from the MAIN tree's directory depth.** MSB1009 "Project file does not exist" when the file is absent; MSB3245 unresolved `Sandbox.*.dll` references after a naive copy when the worktree nests one level deeper (e.g. `dev\\worktrees\<name>\` vs `dev\\ \`). Fix: copy from the main tree into the worktree, then byte-safe-patch every `../../../../../../../Program Files (x86)/Steam` reference one `../` deeper (7→8 for the standard worktrees layout here) — and never commit the copy (it stays gitignored). Hit independently by two parallel build agents in the same session. (, M14 items 2026-07-16) — **More robust than counting `../`:** write the csproj with ABSOLUTE engine paths (`C:/Program Files (x86)/Steam/steamapps/common/sbox/bin/managed/Sandbox.*.dll` and the `addons/base/code/Base Library.csproj` ProjectReference) — depth-independent, so the same file works from any worktree nesting. **AND give each worktree build a DISTINCT `<OutputPath>`** (e.g. `…/.vs/output-wt-<branch>/`): the default `…/.vs/output/` is shared, so two parallel worktree builds (or a worktree + the open editor) clobber each other's `.dll`. Verified a clean 0-warning/0-error build this way from a `--movement-loops` worktree. **Addendum (engine 26.07.22):** VENDORED LIBRARY csprojs (`Libraries/<kit>/Code/*.csproj`) carry the same relative chains and need the same absolute-path treatment; often build them FROM SOURCE (author a gitignored `*.offline.csproj` per kit with absolute engine paths + a scratch output dir) rather than HintPath-ing prebuilt DLLs when the kit source has moved. Then verify twice: sha256 the shared output DLLs before/after for byte-identity (proves the live editor's tree was untouched), and search the built assembly for every new type/convar the pass should have added (a green build proves linking, not that your types landed).

- **`git worktree remove` fails with "Permission denied" on a repo that lives inside a One-synced folder — both on the worktree folder itself and on the `.git/worktrees/<name>` metadata dir.** One stamps read-only/sync attributes on files it manages, and git's delete gives up on them; `git worktree prune` then also fails to clear the metadata, leaving a stale `.git/worktrees/<name>` entry even after the folder is gone. Fix (PowerShell): `Remove-Item -Recurse -Force <worktree-path>` for the tree, then clear attributes on the metadata before deleting it — `Get-ChildItem <repo>\.git\worktrees\<name> -Recurse -Force | % { $_.Attributes = 'Normal' }` followed by `Remove-Item -Recurse -Force`. Verify with `git worktree list` and an `ls` of `.git\worktrees\`. Plan for this on any machine where `dev\` is under `One\Documents` — every agent-worktree cleanup hits it.

- **A Python CLI that prints editor/game console output dies with `UnicodeEncodeError: 'charmap' codec can't encode character` the first time a log line contains an emoji** (s&box logs include them, e.g. the "👋 X has joined the game" line) — Windows Python defaults stdout/stderr to cp1252 when piped. Fix at the top of the script, right after `import sys`: `for s in (sys.stdout, sys.stderr): s.reconfigure(encoding="utf-8", errors="replace")` (or set `PYTHONIOENCODING=utf-8` in the caller). Hit live reading the project's editor console through the MCP client tool.

- **A deterministic asset-generator re-run can show ~100 files as "modified" in `git status` while every one is BYTE-IDENTICAL to the committed blob** — `core.autocrlf=true` with no `.gitattributes` invalidates git's stat cache when a generator rewrites files with the same content. Before believing a regen clobbered anything, prove byte-identity: `git rev-parse ":<path>"` (index blob hash) vs `git hash-object -- <path>` (working blob hash) — equal hashes = zero real change. `git diff --stat` under default autocrlf already collapses to the true logical diff. Reset phantoms with `git checkout -- .` (safe — blobs are identical).

- **A library extraction seam (a delegate/hook that swaps one behavior) tends to cover only the HEADLINE behavior of the code path it replaces; every other side effect of the original code silently disappears unless you inventory and reproduce it on the consumer side.** Before wiring a seam, list EVERY side effect of the replaced path (visual mounting, transforms read from data, timing/telemetry, logging, registration calls), then reproduce the missing ones in a consumer-side wrapper. Physics subtlety: part colliders shift the body's inertia tensor, so assembly differences are telemetry-relevant (handling metrics move), not cosmetic. A green compile says the seam is wired, not that it is complete.

- **When a vendored library ships assets at the same bare resource path as the consuming game's own copies, byte-identity is the escape hatch: verify EVERY colliding file is byte-identical (`cmp`/hash), and if so the collision is behavior-neutral.** The engine picks one copy for a bare path; if byte-identical the pick is unobservable. If ANY pair differs, the game must override/rename its paths. Applies to `.sound` events AND their referenced source audio (check the whole reference chain). Run the byte-identity sweep at vendor time and re-run on every vendor sync.

- **A consumer game plus a vendored library can be compile-gated fully offline (no editor, no generated csproj) by building TWO assemblies with scratch csprojs against the editor install's prebuilt base library DLL.** Recipe: (1) scratch csproj per assembly using `Microsoft.NET.Sdk.Razor` SDK, referencing the install's `Base Library.dll`; (2) `<GenerateAssemblyInfo>false` + fresh `obj` directory per build; (3) build LIBRARY first, then GAME referencing the produced kit DLL; (4) gate on 0 warnings 0 errors. Caveats: no SCSS, no whitelist, `RZ10012` must be treated as error in review.

- **The editor discovers a library under `Libraries/` ONLY if that folder contains exactly one `*.sbproj`; a hand-vendored library without one is silently skipped and every type it defines fails the game compile with CS0246.** Discovery scans at PROJECT LOAD only; zero or two-plus sbproj files both bail silently. Sharp edges: (1) discovery runs only at project load (not on hot recompile); (2) offline `dotnet build` compiles library source directly and CANNOT catch a missing `.sbproj`.

- **`git archive <ref> <path> | tar -x` silently corrupts vendored files on a machine with `core.autocrlf=true` (the Windows default): the command runs the same clean/smudge filters as a checkout, so every file git treats as text gets its LF line endings rewritten to CRLF on the way into the archive, and neither `git archive` nor `tar` prints a single error or warning.** Any downstream byte-count check, hash check, or "matches the source blob" provenance claim then fails for a reason nothing in the command output explains. Measured proof: extracting one `.obj` mesh from a source ref produced a 16411-byte file against a 15893-byte source blob, 518 bytes larger, one extra byte per line ending. Fix: scope autocrlf off for the single invocation, `git -C <source-repo> -c core.autocrlf=false archive <ref> <path> | tar -x -C <dest>` (the `-c` flag does not touch the source repo's persisted config). Verification: don't trust byte counts alone, a file can coincidentally land at the right size while its content still drifted; recompute each extracted file's git blob SHA-1 (`sha1("blob " + len + "\0" + data)`) and diff against `git ls-tree -r -l <ref>` for the source ref, which catches size drift and same-length content drift in one pass. Durable follow-up: add a `.gitattributes` in the destination repo marking the vendored trees `-text` (for example `Assets/models/** -text`, `*.obj -text`) so the destination repo's own commit/checkout cycle can't re-normalize what was just extracted. Related but distinct from `g-tool-autocrlf-masks-regen-determinism-check` and `g-tool-deterministic-regen-autocrlf-phantom-diff`: those cover autocrlf producing a FALSE positive diff on content that never really changed; this one is autocrlf causing a REAL, silent change to bytes that were supposed to be copied exactly.

- **A Python CLI flag that takes a coordinate triple (e.g. `--pos-m -4,-9,2.2`) fails argument parsing whenever the value starts with a minus sign: argparse treats a token starting with `-` as another flag, not as this flag's value, and errors instead of consuming it.** Effect: every coordinate west or south of the origin (any negative X or Y) is unreachable through the normal `--flag value` calling form, while positive coordinates work fine, which makes the bug easy to miss until someone actually needs the far side of origin. Workaround that DOES parse: the equals-form, `--pos-m=-4,-9,2.2`. Argparse only applies the leading-dash-is-a-flag check when the value is a separate token, not when it's joined to the flag by `=`. Fix at the tool level: document the equals-form in the CLI's own usage/help text so callers don't have to discover it by trial and error, or normalize `sys.argv` before parsing (rewrite bare `--flag -x,y,z` tokens to the joined form, or use `parse_known_args` plus manual reattachment) so both calling forms work.

- **`subprocess.run(..., capture_output=True)` turns a child script's early, clean abort into a silent PARENT-side success unless the parent checks the return code and prints the captured stderr.** Live case: a soak harness spawned per-shot evidence-capture children without forwarding the MCP url the parent itself had already resolved; every child aborted immediately with "no MCP url", `capture_output` swallowed that message entirely, and the harness reported success having written zero screenshots — the run "passed" with a clean report for several nights before anyone counted files on disk. Two independent fixes are both required, not either/or: (1) instrument children must not silently default an argument they cannot infer — forward every required argument (here, the MCP url) explicitly from the parent, resolved once; (2) the parent must check `returncode != 0` and print the child's stderr (or last line of stdout) on failure, never trust a bare exit-code-shaped call as proof of work done. - **One branch adding a member to an interface, while a parallel branch adds a NEW implementer of that same interface, is a semantic conflict git's own merge machinery cannot flag, because neither branch's diff touches a line the other branch touched.** Each branch compiles clean on its own; each branch's own gate is green; the merge itself resolves with no textual conflict at all. The combined code fails only when something actually COMPILES the merged tree, at which point the new implementer is missing the new member. Nothing about `git merge`'s conflict detection can catch this class of break, it is only ever visible to a compiler, and only after the merge lands. **The honest gate after ANY merge that touches an interface, a base class, or an enum consumed by a switch is resolving a symbol that is NEW to the merge from each side**, not just re-running the existing test suite (which was written before either branch's addition existed and cannot exercise it). With a live editor this recipe needs one more step layered on top: `compile_status` reading green is not proof the resolve actually ran against the freshly merged code, a stale loaded assembly can report a clean compile while still serving the PRE-merge symbol table (`g-tool-green-compile-status-not-loaded-assembly`) — so the post-merge check is not "does it compile", it is "does `get_component_type` (or equivalent) resolve a symbol that exists ONLY after this merge, on a freshly loaded assembly." **SIBLING CASE (engine 26.07.22) — compiles clean AND runs wrong:** the same adjacent-line blindness also merges two independent edits on neighbouring lines into behavior neither branch intended (one branch swaps a world-build call, the other had added a sky/time-of-day call on the line beneath hardcoded to the old arena), and a new-symbol-resolve gate PASSES because every symbol exists. The honest post-merge gate is symbol-resolve PLUS a behavioral check on the merged hotspot (run it, assert an observable the merge should have changed). Adjacent lines in a small bootstrap are the highest-value place to look; fix by publishing the shared fact as ONE value both call sites read.
