> for a matching bullet's full write-up, follow that gotcha's article link in `coverage.md`

- **Editor-embedded play mode is hard-capped at the desktop's vsync (60 Hz) and it is NOT
 liftable via any cvar.** `r_frame_sync_enable 0` AND `fps_max 0` were both confirmed set
 (read the value back — it echoes "0") and fps still pinned at EXACTLY 60.0 (300 frames / 5 s
 window). The cap is the compositor's vsync on the editor window's present, not the engine
 frame-sync. Consequence for any perf study driven through the editor MCP loop: you CANNOT
 measure the true GPU ceiling — `avg = 60.0` only means "the engine met every 60 Hz deadline".
 The real knee is `avg < 60` WITH a collapsing p1 (1% low). one project held a locked 60 fps
 up to 2.03 M render tris / 2304 draw calls / 900+ static ModelColliders — render never bound.
- **For a chunked runtime-mesh generator, REGEN (single-threaded generation CPU) is the binding
 resource, not fps or draw calls — and regen is generation-math-bound, not scene-object-bound.**
 the project's regen grows ~linearly with cell count (WorldSize²): 384²≈0.4 s → 1024²=2.3 s →
 1280²=3.6 s → 1536²=5.4 s (the wall — busts a 5 s budget). Decisive evidence it's the passes not
 CreateObject/collider build: bumping ChunkCells 32→64 QUARTERED the GameObject/ModelCollider
 count (1024→256 chunks) at 1024² with ZERO regen change (2286 vs 2257 ms). So the lever to push
 density further is THREADING the pure passes (GameTask.RunInThreadAsync), never bigger chunks.
 Corollary: don't raise ChunkCells for a draw-call reason — draw calls never bound fps here, and
 smaller chunks keep finer dirty-remesh granularity for a brush editor.
- **Voxel GRAIN (CellSize) is nearly free; the density knob the art wants costs almost nothing.**
 At a fixed WorldSize, CellSize 0.5→0.4→0.3 m barely moved tris or regen (512² all ~315 k tris,
 ~580 ms) — CellSize only changes the physical footprint, not the cell COUNT that drives cost.
 StepHeight 0.25→0.125 m costs +~54% tris and drops greedy efficiency (finer steps split
 same-height runs: 2.1→1.6×) but fps/regen stay flat. So "smaller blocks" = raise WorldSize AND
 shrink CellSize proportionally to hold the footprint: finer grain at constant perf AND constant
 scatter density (scatter is a fixed INSTANCE budget, so a constant footprint preserves density;
 a bigger footprint dilutes it).
- **fps-probe measurement hygiene through the MCP loop:** `read_console` accumulates lines across
 play sessions, so (1) delimit "this session's" fps lines by the fresh `[boot] boot:` marker that
 each play_start logs, (2) DROP the last window (it carries the play_stop hitch — shows a false
 p1 like 0.5/29), and (3) sample ≥3 clean windows (≥18 s play): a 1-window sample routinely
 catches a stray hitch and reports a bogus avg=48/p1=28 for a rung that actually holds a rock-solid
 60. Skip a warmup (~1.5 s) in the probe so the play-start world-build hitch never poisons window 1
 — but if the build itself exceeds the warmup (>1.5 s regen), it still bleeds into window 1.
 Also: a game-assembly static (WorldGen.CurrentSpec) SURVIVES the editor→play boundary (same
 process, no assembly reload), so you can benchmark an editor-generated spec in play mode by
 having Bootstrap read that static.
- **In the fidelity-ladder's FIXED-EXTENT mode, halving the voxel grain QUADRUPLES the cell count (WorldSize doubles per side), so tris and regen scale ~4× — the opposite of the fixed-WorldSize case where grain is nearly free.** To hold a constant physical footprint at a finer grain you must DOUBLE WorldSize (192 m = 480@0.4 / 960@0.2 / 1920@0.1), and 1920² voxel busts the 2 M tri budget (~3.7 M) and the ~5 s regen wall. Measured at a 128 m footprint: 320²@0.4 = 122 k tris / 0.26 s, 640²@0.2 = 478 k / 0.9 s, 1280²@0.1 = 1.877 M / 3.9 s (under 2 M — the safe fine rung; = the doc's "1280 max rung"). So a cross-grain sweep must cap the finest tier at ≤ ~1280² for voxel. LowPoly / Smooth stay cheap at fine grain (HeightfieldDecimation=2 → 824 k tris @ 1280², no tier-aware decimation needed).
- **To perf-ladder a PHYSICS workload in the vsync-capped editor, time the engine physics step directly via `IScenePhysicsEvents.PrePhysicsStep`/`PostPhysicsStep` + a Stopwatch — frame fps is masked (avg pins at 60), but the step time is the true, vsync-free CPU cost.** A component implementing the interface gets both callbacks around the real 50 Hz solver step (250 samples per 5 s window confirms cadence); log avg + worst-1% step ms per window next to the fps p1. Whitelist-clean in-editor. MEASURED with it ( limits ladder, vp raycast-wheel cars on a 1024^2 WB heightfield): per-car part/collider count is effectively FREE at roster scale — a small BoxCollider compound-folded into a car Rigidbody costs ~0.9 us/step, an entire idle kit car ~13 us/step; 16 cars + a 128-collider car = 0.39 ms avg / 0.78 ms p99 of the 20 ms tick (2%/4%), p1 fps dip ~2%, no knee anywhere in 16->128 parts, 16->128 colliders, 1->16 cars. Corollary for car-roster budgeting: the binding resources are world REGEN CPU (~2.5-3 s single-threaded at 1024^2, the known M7 finding) and dent-rebuild TRIANGLE cost — spend the advanced-tier budget on panel tessellation, not on part-count anxiety.
- **A per-frame-rotating shadow-casting `DirectionalLight` (the sun, `WorldRotation` reassigned every play frame → cascade rebuild) is NOT an FPS-breaker at scale — measure before you "fix" it.** perf-pass phase 2 ran the isolation matrix expecting the sun-shadow rebuild to be THE cause of an owner "really low FPS" report; it was refuted. Play mode held a locked, vsync-capped 60.0 fps (p1 ~55-57, p99 ~17.5-18 ms) across EVERY cell, from the 960 default (1400 renderers / 1400 shadow casters) up to 1920 + max props/town/wildlife (**9633 renderers, 6025 shadow casters, 3600 colliders, 2.47 M tris, 24 O(N) critters**), orbit AND character view. Decisive block D at the heaviest cell: **D2 (clock PINNED) = D1 (clock running) = 60.0** → per the protocol's own criterion (refuted if D1≈D2) the sun-shadow hypothesis is refuted; C2 (Smooth per-chunk materials, 960 = 60) and C3 (draw-call ceiling, 9633 = 60) fell too. METHOD TRAP under the vsync cap (`g-perf-editor-embedded-play-mode-hard-capped`): `` measures wall-clock, so it cannot see GPU headroom BELOW 60 — a hypothesis is only testable by overloading until `avg<60`, and if even max-everything holds 60 with a healthy p1 the hypothesis is *refuted-or-vsync-hidden*, not confirmable. Confirm `fps_max` is already `0` (it is — flat 60.0 regardless); `r_vsync`/`vsync` are unknown commands, so you cannot uncap the windowed editor. The per-frame sun write IS wasted work by code inspection but is absorbed by headroom here — a rotation-delta throttle (skip the `WorldRotation` write below ~0.1-0.15° of sun-forward movement, keep colours per-frame) is READY but was deliberately NOT shipped (no reproduced sub-60 case to validate a recovery; would move no number under vsync).
- **The whole editor-side perf-probe surface is reachable from GAME-assembly code, whitelist-clean — no engine `BenchmarkSystem` needed for RELATIVE numbers.** `Sandbox.Diagnostics.FrameStats.Current` (`DrawCalls`/`TrianglesRendered`/`ObjectsRendered`/`ObjectsPreCull`/`ShadowMaps`/ `ShadowedLightsInView`, all `double`) and `Sandbox.Diagnostics.PerformanceStats` (`Gen0/1/2Collections`, `BytesAllocated`) compile + run in a play-mode `Component` (confirmed `PerfProbe`, re-confirming ' `BenchmarkHarness`). Combined with per-frame `RealTime.Delta` (frame pacing) and the `IScenePhysicsEvents` Pre/PostPhysicsStep + `Stopwatch` physics-step timer (`g-perf-physics-step-stopwatch-vsync-free`), that is the complete editor-relative instrument: frame ms + physics ms + draws/tris/objects + GC, one grep of `[vp] PERF` lines. Read every engine-stat field inside try/catch so a future rename degrades a field to -1 instead of breaking the frame baseline. STILL not measurable this way: the true GPU ceiling / absolute FPS — editor Play is vsync-hard-capped (`g-perf-editor-embedded-play-mode-hard-capped`), so avg pins at 60 and GPU cost below 16.7 ms is invisible; take absolutes from a standalone/benchmark build. FINDING from the vp Phase-0 baseline: a low-poly SINGLE-car raycast-wheel scene is trivially cheap on every measurable axis — physics step ~0.02 ms idle / ~0.04 ms driving of a 20 ms tick (~0.1-0.25%), GC exactly zero over 20 s, no shadows rendered — so the ONLY number a min-spec-GPU pass would care about is draw-call count (~1000 for the city buildout, each static box its own draw), and that is precisely the number the vsync cap hides. Measure-first verdict: within budget, no CPU/physics/GC optimization warranted.

- **On a perf ladder where a rung's own setup spawns many physics bodies in a single frame, WINDOW 1 is garbage at EVERY rung by design, not just the noisy ones — the spawn frame itself hitches, so window-1 p1 readings of 10-12 fps show up even on rungs that are otherwise a perfectly flat, healthy line.** Measured spawning 256 rigidbodies per rung: the aggregator must drop the first (and last) window for exactly this reason, or a reader who trusts the raw per-window numbers will see a false knee at every single rung and conclude the whole ladder is broken. Same family as the world-scale density study's window-0 warmup-hitch rule (`g-perf-fps-probe-measurement-hygiene-through-mcp`, this file) but a distinct trigger: that one is a play-mode BOOT hitch cleared by a warmup; this one is a MID-LADDER spawn hitch that recurs on every rung and has to be dropped by the aggregator's design, not worked around by a warmup.
