# Writing gameplay — networking & multiplayer

> Topic sub-file of this lane — router: `writing-gameplay.md` (its "Where everything lives"
> table maps every topic). Load `_core.md` first. Bullets below are moved verbatim
> from the lane pack; the sync appends new bullets for these topics here.

- **Owner-simulated character spawn: implement `INetworkListener.OnActive(Connection)` on a
  host component and `go.NetworkSpawn(channel)` there.** `OnActive` fires for the host's OWN
  connection (#0) too (so the host gets a character), but `OnDisconnected` does NOT fire when
  the host itself leaves — only when a remote peer drops. The engine calls
  `INetworkListener` methods only on the host, so no `Networking.IsHost` guard is needed.

- **To exercise the full networked-spawn path with one peer (no second machine),** call
  `Networking.CreateLobby(new LobbyConfig())` from an editor MCP tool through a
  game-assembly static bridge — never call `CreateLobby` from the editor tool thread; it
  must run on the game main thread (consume the request in a play-mode component's
  `OnUpdate`). This sets `Networking.IsActive` true and runs the real spawn/sync path,
  letting you verify component creation order and `[Sync]` wiring without a second peer.

- **An overhead UI element (name tag, health bar) anchored to a per-player gameplay field
  FREEZES over a remote player's spawn position while their model walks away** — if that
  field is not `[Sync]` and written only inside the owner's `OnFixedUpdate`. A proxy never
  runs the owner's tick, so the field is stuck at spawn. Fix: anchor off the live networked
  transform (`WorldPosition`), which is replicated and engine-interpolated.

- **A `[Sync(SyncFlags.FromHost)]` field on a runtime-created singleton does NOT replicate
  unless that object is `NetworkSpawn`ed.** A `Scene.CreateObject()` singleton has no
  cross-peer identity even with `NetworkMode.Snapshot`. `GameObject.Network.Active == false`
  and the field never crosses the wire. Fix: host-`NetworkSpawn()` the singleton; the joining
  client receives the host's networked proxy instead of creating its own local copy.

- **On the host, spawning a joiner's character clobbers the host's camera-target singleton:**
  `Components.Create` runs BEFORE `NetworkSpawn(owner)`, so `IsProxy == false` at create time
  and an `OnEnabled` that claims `static Instance` behind `if (!IsProxy)` grabs the joiner's
  body. Fix: re-resolve the claim at the first `OnFixedUpdate`, where `IsProxy` is trustworthy.

- **A joining client's static join state (invite code, mode) gets WIPED by the networked scene
  handoff:** `Networking.Connect` loads the host's scene, the bootstrap creates a new instance,
  and its `OnEnabled` "reset for a fresh session" runs before the join handshake sends those
  values. Fix: make `OnEnabled` reconstruct-not-reset when already connected as a non-host.
  Test blind spot: `-joinlocal` never sets a code pre-handoff, so it can't catch this.

- **A PUBLISHED-build client join RELOADS the game assembly, wiping ALL statics** — the
  reconstruct-not-reset fix has nothing to reconstruct from. Fix: persist join intent to
  `FileSystem.Data` before `Networking.Connect`; restore from disk after the reload, gated
  on a freshness window. Only a real cross-machine published join exercises this path.

- **`Networking.CreateLobby()` is ASYNC — `Networking.IsActive` is still false on the same
  frame.** Any branch on `IsActive` immediately after `CreateLobby` takes the wrong path.
  Gate on your own synchronous mode enum (set on the same frame). Also: a session-END path
  must un-possess the character (`ExitCharacter()`) to restore the pre-session view.

- **Pointing a dedicated server at a published-style ident that is not actually published yet
  boots the engine, connects, then fails with `Unable to download package` — and the server does
  NOT self-exit, it lingers holding the process.** Distinct from the client-side join wall where a
  LOCAL `.sbproj` host + joining client dies on `Package wasn't found!`. Kill the server with a
  timed launch + kill-by-PID pattern. Expected to resolve once the package is actually published
  (Hidden should be sufficient).

- **Making an editor→play STATIC-bridge command/telemetry path multiplayer-safe: keep the bridge `static` (it is a per-PROCESS editor-harness instrument — the editor has no `Connection` and drives the one local player), and instead ownership-gate the CONSUMER with `if ( IsProxy ) return;`.** The load-bearing fact that lets you land this as its OWN milestone, BEFORE any `NetworkSpawn` wiring exists: `Component.IsProxy` is FALSE on a non-network-spawned runtime object (it is `Network.Active && !Network.IsOwner`, and `Network.Active` is false until something spawns the object networked), so a blanket proxy gate on `OnFixedUpdate`/`OnUpdate` is a pure no-op in single-player — behavior stays byte-identical while pre-installing the guard a later networked-character milestone needs. Put ONE `if ( IsProxy ) return;` at the top of the tick method that owns the movement/telemetry (every bridge report-field write lives under it or what it calls) rather than sprinkling per-writer guards. Also gate the `public static T Instance` claim on `!IsProxy` (`OnEnabled { if ( !IsProxy ) Instance = this; }`) so a remote player's proxy can never become "the" local Instance that a camera or director reads — else the local view/autopilot would follow someone else's citizen. Prove no telemetry field went dead with a baseline-vs-after functional run on the SAME route (single-player: reached / fall-throughs / maxSpeed / swim-slide flags must match). The parked vehicle lane already demonstrated the pattern is single-player-safe in-repo — its `OnFixedUpdate` opens with `if ( IsProxy || !Body.IsValid ) return;` and the suite stayed green. Structure the character SPAWN as `SpawnCharacter( Connection owner )` (owner = `Networking.IsActive ? Connection.Local : null`) so the per-connection `go.NetworkSpawn( owner )` slots in later without reshaping the call site — but do NOT add the `NetworkSpawn`/`[Sync]` yet, that overshoots into the next milestone.

- **Replicate a host-authored config that drives deterministic regeneration as its canonical JSON STRING on a `[Sync(SyncFlags.FromHost)]` field — not as a networked record — and observe it on clients with an `OnUpdate` POLL, not a `[Change]`/`On[Prop]Changed` hook.** Three verified facts behind this ( M12.1, `WorldSession.NetSpecJson`): (1) `WorldSpec` is an init-only, append-only C# `record`; relying on the engine's networked-record support is an unforced risk, whereas a string is the most boring thing `[Sync]` handles and the `Json.Serialize`/`Deserialize` round-trip is already battle-tested by save/load. (2) The `[Change]` attribute DOES exist on this build (`Sandbox.Engine.xml` `T:Sandbox.ChangeAttribute`: "invoke a method when the property changes … If no name is provided we call `On[PropertyName]Changed`"), but it is not proven to fire for a `FromHost` field delivered by SNAPSHOT (not an owner set) — so use the proven Minimap-`Generation` poll idiom instead: cache `_lastApplied` and compare the observed value each `OnUpdate`; it fires regardless of HOW/WHEN the snapshot lands. (3) Publish from INSIDE the single choke-point regenerate method, AFTER success, gated `if ( !Networking.IsActive || Networking.IsHost )`, and stamp `_lastApplied` to the just-published string so the host's OWN poll never self-echoes; the client's poll is additionally gated to non-host so single-player (`Networking.IsActive` false) is a pure no-op (byte-identical output, proven by the determinism suite staying green with the field added). Order law: publish LAST after a successful build so a spec that failed validation is never broadcast — a client only ever sees a world the host itself built.

- **A host-authoritative handshake on a Snapshot singleton = instance `[Rpc.Host]` client→host + `[Rpc.Broadcast]` wrapped in `using (Rpc.FilterInclude(Rpc.Caller))` host→one-client, with the broadcast body guarded `if (Networking.IsHost) return;` — and factor the COMPARE out of the RPC into a pure static so it's unit-testable headlessly.** M12.1's grid-hash handshake (`WorldSession.ReportWorldHash`/`ResolveHandshake`) copies ' confirm-to-caller idiom onto a Bootstrap-created Snapshot singleton (one `WorldSession` per peer, so the instance RPC's target is unambiguous). Two load-bearing moves an agent can fully verify on ONE machine even though the two-peer routing itself is owner-gated (D10): (a) put the comparison in a pure `static bool CompareAndLog(name, host, clientFull, clientSubs, out sub)` that emits the two canonical log lines (`[wb] handshake OK client=<n> hash=<h>` / `[wb] DESYNC client=<n> sub=<pass>`), then it from a `[McpTool]` self-test that feeds a deliberately corrupted sub-hash then the matching one — BOTH lines fire in the editor console with no second peer. (b) The runtime handshake needs the hash algorithm that previously lived in an EDITOR-assembly `[McpTool]`; extract it to a shared GAME-assembly static (`WorldHash.Compute`) and funnel the editor tool through it — do NOT duplicate — keeping the byte layout identical so existing determinism-suite hex is unchanged. HONEST CAVEAT (same as EnclosureGate): whether a Snapshot object's instance RPC actually reaches the host's matching instance is still owner-verify-pending; if a live two-peer run shows `reporting hash=…` on the client with no host `handshake OK`/`DESYNC` receipt, fall back to a scene-singleton dispatcher. All `[Sync]`/`[Rpc.Host]`/`[Rpc.Broadcast]`/`Rpc.Caller`/`Rpc.FilterInclude`/`Networking.*` usages passed the in-editor whitelist compile.

- **A component with `[Sync]` vars created in `OnStart` (i.e. AFTER `NetworkSpawn`) never replicates — each peer creates its OWN local instance and the [Sync] pair silently never matches.** M9-C put the boost state's `[Sync] (BoostId, ExpiresAt)` on a boosts component that the character controller's OnStart added via `Components.GetOrCreate<>` — the established pattern for the (sync-free) contact/stack helpers. NetworkSpawn runs BEFORE OnStart, so the component wasn't in the spawn snapshot: the owner wrote BoostId=1 and the host probe showed it, but the client's proxy instance stayed at 0 forever, with no error anywhere. Fix: create the component in the SPAWN PATH, before `go.NetworkSpawn(owner)` (beside the controller and visual components); OnStart's GetOrCreate then FINDS the replicated instance on every peer. Rule of thumb: components that only READ/tick locally may be created any time; a component that carries `[Sync]` state must exist pre-NetworkSpawn.

CAVEAT — this does NOT by itself prove (b) is broken: Steam `ISteamMatchmaking` commonly **excludes lobbies the querying client is already a member of** and can lag indexing a just-created lobby, so a self-query is a **structurally weak probe** — `foundSelf:false` is equally consistent with "(b) works fine for a real second peer, never for self." - **To join a friend-hosted Steam lobby by a SHORT human code, the lobby must be VISIBLE (`Hidden=false`) — hidden lobbies are excluded from `QueryLobbies` (the engine forces `hdn=0`, see `g-game-hidden-lobby-self-query-returns-nothing`) — but a visible lobby's metadata is enumerable by anyone running the game, so DON'T put the plaintext code in `SetData`. Enumeration then reveals only that a lobby EXISTS (its hash), never the code, and a raw connector who skips the query still can't pass the host's wire check. Getting the host's OWN lobby id from game code (for an id-encoded backup code, or any lobby-id need) has **no public synchronous API** — the socket's `LobbySteamId` is `internal`; the only game-code route is a self-`QueryLobbies` against the now-visible lobby, reading `LobbyInformation.LobbyId` (match `OwnerId == Connection.Local.SteamId`), which is async + subject to metadata-propagation lag so it must be retried — **and coordinator live probes (same day) show it NEVER resolves: the host's own visible lobby was still absent from its own hash-filtered query after 3.5 minutes (probes at 30 s / 48 s / 3.5 min) — SELF-QUERY EXCLUSION holds for visible lobbies too, so a host cannot learn its own LobbyId at all and any host-side id-encoded backup-code scheme is structurally dead until a public own-lobby-id API exists. - **A batch of networking API facts, source/XML-verified against the installed build, that overturn common assumptions when planning multiplayer code before it ever touches the compiler:** - **`LobbyInformation` is a STRUCT, not a class.** Code that null-guards it (`if (info == null)`) does not compile; guard against a default-constructed value instead. - **`Networking.Connections` is deprecated** ("Moved to `Connection.All`"); the compiler emits CS0618. Use `Connection.All` everywhere instead. - **`Connection.MaxChunkSize` is `internal`**, not reachable from game code, even though its value (128 KB / 131072) is real and is the documented auto-chunk threshold. Game code that needs the number has to hard-code it (or stay well under it) — the symbol itself is unreferencable, the value is not wrong. - **`NetworkAccessor` has no settable `Owner`, `OwnerTransfer` or `OrphanedMode`** — all three are get-only. The mutators are methods, called AFTER `NetworkSpawn`: `AssignOwnership`, `SetOwnerTransfer`, `SetOrphanedMode`. - **`Networking.TryConnectSteamId` DOES exist and is public**, despite some docs/plans assuming otherwise; `Networking.Connect(ulong)` is the shorter equivalent path most code should reach for, but the method exists and the API surface question is closed. - **SB1000 whitelisting is ASSEMBLY-level, not per-member.** `Sandbox.Compiler` permits any reference whose assembly name starts with `Sandbox.` or `Facepunch.`, and `Sandbox.AccessRules` whitelists `Sandbox.Engine`/`Sandbox.System` outright. Every stock networking API lives in one of those two, so "is this networking call whitelist-safe" is not actually the risk for networking specifically — **public vs `internal` accessibility is the real constraint** (see `MaxChunkSize` above): an API present in the engine XML can still be unusable from game code for that reason alone, nothing to do with the whitelist. - **`dotnet build` green does not mean editor-green for networked types.** The headless build does not run the editor's compiler, its analyzers, or its type registration, so a networked component only fully resolves at the editor's own compile — treat a headless-only pass on networking code as provisional until an editor merge/compile confirms it.

- **A dedicated server process never creates a Steam lobby at all — `Networking.CreateLobbyAsync` branches on `Application.IsDedicatedServer` straight into `CreateDedicatedServer` -> `DedicatedServer.Start`, which drives `ISteamGameServer` and never touches the lobby socket.** Any lobby-creation code path built and tested against an editor-hosted or standalone-hosted lobby (the normal development case) will silently do nothing useful when the same binary runs as a dedicated server — there is no lobby to query and no lobby id to read off a `LobbyInformation`, because the object was never created. The joinable identity instead comes from `Sandbox.Utility.Steam.SteamId`, and it is set ASYNCHRONOUSLY by a Steam callback that lands AFTER the server's own launch log line, so a launch script that logs "server ready" and immediately reads the SteamId can read it before it exists. **Consequence: a dedicated-server bring-up needs its own path, separate from whatever lobby-creation code the game already has for peer-hosted play.** Practical fix: a short repeated poll (a few seconds) that logs the SteamId once it becomes non-zero, since there is no event/callback surface exposed to game code for "the Steam ID is now ready." **Corollary: headless dedicated-server join is direct-connect only** (by the polled SteamId or IP), never lobby-browser discovery, because the discovery mechanism (the Steam lobby) is the exact thing that was never created for that process.
